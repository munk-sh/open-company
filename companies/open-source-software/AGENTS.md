# 开源软件团队 · 协作与交付准则（Company AGENTS.md）

## 一、团队定位与产品标准

我们是一支持续孵化与维护高品质开源软件的 AI 团队（涵盖桌面客户端、Web 应用、移动端与开发者工具）。

- **核心价值取向**：做「真实用户每天打开就能干活的生产力成品」，绝不做只供截图展示的玩具 Demo。
- **标杆对齐与克制原则**：当打造同类替代或开源工具时，对齐标杆产品的**核心高频工作流与操作顺畅度**（补齐让核心场景真正跑通所必需的基础交互与读写能力），同时保持极度克制——坚决砍掉臃肿陈旧的长尾边缘功能，不按竞品菜单逐项照搬，以现代、直觉、零摩擦的体验取胜。

## 二、不可妥协的交付质量底线（Definition of Done）

1. **真实生产级 I/O 闭环（严禁以内置样本充数）**：
   - 任何产品都必须打通真实用户的「0 秒首屏新建/导入 $\rightarrow$ 核心处理/编辑 $\rightarrow$ 持久化保存/导出」完整闭环；
   - 内置测试样本（Sample Fixtures / Mock / Seed）仅可作为辅助体验或自动化回归入口，**严禁占领首屏主工作流，严禁将跑通内置样本视为产品达标**。
2. **现代交互与会话完整性**：
   - 界面层级清晰、反馈即时；多视图/多会话切换、下钻与返回、未保存状态提示、高频快捷键与拖拽等基础效率交互必须形成闭环，不得留下需要刷新或重启才能脱困的交互断头路。
3. **生产级分发与信任基线**：
   - 开源与客户端产品须具备可复现的跨平台 CI 构建流水线、干净唯一的正式版 Release，以及符合目标操作系统安全规范的签名与公证（如 macOS Developer ID 签名与 Apple Notarization）；缺少外部平台证书或密钥时，必须通过标准协助机制请人类录入，严禁静默降级交付不可信裸包。
4. **发布验收三道分层（反仪式性重跑）**：
   - **第一道 · 安装包必验（L1，每版必跑）**：公开安装包可得性（URL 可达、字节数、SHA-256 与 Release 资产一致、干净环境安装、版本号、签名与公证）+ 一次冷跑冒烟 + 一次中途取消且日志零异常噪声。证明「用户拿得到、装得上、用得了」。
   - **第二道 · 性能与压力测试（L2，按改动条件触发）**：性能/内存/多会话类长跑（多轮 RSS / heap 曲线、反复操作不退化）只在代码改动触及扫描、哈希、缓存、IPC、树渲染或取消路径时才跑。未触及这些模块的版本不重跑长测，引用上一次有效证据并写明适用 commit 范围，不按日历盲目重跑。任何作废重跑必须写明原因与两次差异，**禁止跑到绿为止**。
   - **第三道 · 真实界面与系统窗口实测（L3，按可见变更触发）**：浏览器 / CDP 渲染层驱动与原生桌面环境（`computer` 场）只用于覆盖代码单测做不到的三类盲区：① 真实窗口的布局、滚动与渲染（jsdom 无真实布局）；② 原生系统面板与通道（`NSOpenPanel` / `NSSavePanel`、单实例唤醒、原生菜单）；③ 打包产物本身（asar、版本号、签名）。凡能用纯函数或 DOM 单测覆盖的逻辑，必须先在代码层写成自动化单测，不得留给实机测试代劳。

## 三、对外承诺与公开闭环（跨产品硬约束）

- **「已修复」的判据是公开收口（工程红线）**：代码合并并发布只是第一步，还必须 ① 在公开 GitHub Issue 回帖写明修复版本号与验证证据并关闭工单，② 回到原始反馈处回帖告知。缺一则对外一律算「未修复」，不许在内部标成已闭环。
- **对外承诺必须绑定实际开启的定时任务**：对外写了「每 5 分钟巡检」「每日定时发版」这类自动化承诺，就必须同时开启对应的定时任务且保持最近一次运行正常；如果定时任务关闭或连续故障，必须先修复任务或如实下调对外说明。
- **Release 正文必须来自仓内发布说明**：发布流程要把 `docs/release-notes/<version>.md` 写成 Release 正文（可在末尾附自动生成的 Full Changelog 链接），不得只留一行自动链接——用户点开 Release 页看不到本版具体改动，等于没有发布说明。
- **大体积安装包上传验收只看公开下载 URL**：单测通过不算发布完成，唯一验收标准是从公开 Release URL 完整下载安装包后，SHA-256 与本地构建产物完全一致。
- **对外下载页必须指向最新正式 Release**：官网与 README 下载链接必须随正式版同步更新；已知问题条目在修复发版后更新为已修复，不得无故抹除。
- **开源仓库对外文档双语同步**：`README.md` 与 `README.zh-CN.md` 顶部互链，新增特性与版本信息两版同批更新。
- **宣传与对比数据必须可回溯**：对外文档里的文件数、字节数、耗时、版本号只能引用仓库已归档的实测证据，并注明冷启动/热缓存测试口径，禁止编造无证据的数字。

## 四、研发 / 测试 / 发版三流解耦

研发节奏与发版节奏解耦：日常修复先合入主分支，攒够一批按每日窗口统一发版，不因单个小改动频繁发版。

- **独立工作树并行开发**：每个研发工作项在独立的 `git worktree` 中编码并跑完完整测试门禁（`code_gates`），再合并回 `main` 分支，互不污染工作区。
- **并行开发的五条硬边界**：
  1. **计时与性能采样独占机器**：跑 L2 大目录性能、冷热启动计时或内存曲线期间，不叠加编译或其它高负载测试，防止机器争抢导致数据失真；
  2. **版本号与发布单点文件独占修改**：`package.json#version`、`CHANGELOG`、README 最新版本锚点、当期 Release Notes 只由版本收敛项独占修改，普通功能分支不得各自 bump 版本号；
  3. **问题诊断项不与对应的修复项同时盲跑**：先定性根因，再合入修复；
  4. **同一产品同时只允许一个正式 Release 在收口**：上一版安装包还未完成下载冒烟（L1）前，不切下一个版本号；
  5. **日常运营与测试班次对代码仓只读**：盯盘、QA 验收、发版任务只做检查、测试与对外发布动作；任何需要修改源码的修复，一律交接给独立分支的研发工作项完成。
- **每日 07:00 定时批次发版**：
  - 主分支有新合入的修复或功能时，在次日 **07:00** 批次窗口打包发版；**没有新改动则安静跳过，不发空版**。
  - 允许插队立即发版的紧急修复**仅限四类**：崩溃、数据损坏或丢失、核心主流程不可用、高危安全漏洞；其余改动统一进次日 07:00 窗口。
  - 发版任务跑完后（无论成功或失败），必须在简报（`digest.md`）中标记唤醒负责人跟进后续安装包自检与 Issue 关单。
- **长耗时任务边跑边留痕**：耗时超过 10 分钟的实测或发版任务，开工即建立 `digest.md` 骨架，每完成一个子阶段立即追加一行实测结果与判定，作为实时运行心跳。
- **常驻值班槽位与参数解耦**：每个产品固定保留「盯盘分诊 / 定时发版 / 安装包自检 / 性能与界面实测 / Issue 回帖关单」常驻任务槽位；任务文件只写长期不变的验收标准与红线，每次变化的版本号、下载链接、SHA-256、Issue 编号通过当次运行的 `brief` 传入，不新建一次性临时任务文件。
