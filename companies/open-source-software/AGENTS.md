# 公司投资备忘录与工程宪章（Company AGENTS.md）

## 一、公司定位与产品哲学

我们是一家 AI 原生软件产品公司，致力于持续孵化并交付高品质、开箱即用、可真正替代高价商业软件或解决高频痛点的现代实用软件（涵盖桌面客户端、Web 应用、移动端与开发者工具）。

- **核心价值取向**：做「真实用户每天打开就能干活的生产力成品」，绝不做只供截图展示的玩具 Demo。
- **标杆对齐与克制原则**：当孵化平替或同类竞争产品时，对齐标杆产品的**核心高频工作流与操作顺畅度**（补齐让核心场景真正跑通所必需的基础交互与读写能力），同时保持极度克制——坚决砍掉传统软件臃肿陈旧的长尾边缘功能，不按竞品菜单逐项照搬，以现代、直觉、零摩擦的体验取胜。

## 二、不可妥协的交付质量底线（Definition of Done）

1. **真实生产级 I/O 闭环（严禁以内置样本充数）**：
   - 任何产品都必须打通真实用户的「0 秒首屏新建/导入 $\rightarrow$ 核心处理/编辑 $\rightarrow$ 持久化保存/导出」完整闭环；
   - 内置测试样本（Sample Fixtures / Mock / Seed）仅可作为辅助体验或自动化回归入口，**严禁占领首屏主工作流，严禁将跑通内置样本视为产品达标**。
2. **现代交互与会话完整性**：
   - 界面层级清晰、反馈即时；多视图/多会话切换、下钻与返回、未保存状态提示、高频快捷键与拖拽等基础效率交互必须形成闭环，不得留下需要刷新或重启才能脱困的交互断头路。
3. **生产级分发与信任基线**：
   - 产品的完成定义必须对齐其目标分发形态：开源与客户端产品须具备可复现的跨平台 CI 构建流水线、干净唯一的正式版 Release，以及符合目标操作系统安全规范的签名与公证（如 macOS Developer ID 签名与 Apple Notarization）；缺少外部平台证书或密钥时，必须通过标准协助机制请人类录入，严禁静默降级交付不可信裸包。
4. **发布验收分层（反仪式性重跑）**：
   - **每版必验（L1）**：公开件可得性（URL 可达、字节数、sha256 与 Release 资产一致、干净环境安装、版本号、签名与公证）+ 一次冷跑冒烟 + 一次中途取消且日志零取消噪声。证明「用户拿得到、装得上、用得了」。
   - **条件触发（L2）**：性能/内存/多会话类长跑（多轮 RSS / heap 曲线、反复用不退化）只在 diff 触及扫描、哈希、缓存、IPC、树渲染或取消路径时才跑，并按当期 goal 的阈值判定。未触及这些模块的版本不重跑长测，引用上一次有效证据并写明适用 commit 范围，不按日历重跑。
   - 长跑是为捕捉只在第 2、3 轮才暴露的退化；同一架构行为已被证明后重复测量，只会放大机器噪声。任何作废重跑必须写明作废原因与两次差异，**禁止跑到绿为止**。
   - **门禁分层（禁止把长跑挂进每次交付）**：性能/内存/多会话类采样脚本不得作为每次交付默认执行的 `code_gates` 项——它们是 L2，只能由命中相关 diff 的条件 profile 调用，或作为里程碑版（`x.y.0` / 每 4 周）的独立验收任务一次性跑。同一被测对象在同一 commit 上只采样一次；结论已出就不得为「再确认一次」重起，重跑须先写清作废原因。
   - **实机验收是 L3，只补金字塔盲区，不设每版必跑**：浏览器 / CDP 驱动与原生 computer 场属 L3，只用于覆盖测试金字塔**结构上做不到**的三类：① 真实窗口的布局、滚动与性能（jsdom 无布局、无合成器）；② 原生面板与系统通道（NSOpenPanel / NSSavePanel、单实例接管、原生菜单）；③ 打包产物本身（asar、UA 版本号、签名）。凡能用纯函数或 jsdom DOM 断言覆盖的交互语义（状态聚合、点选跳转、重置、空态、计数一致性）必须先在代码层落成可回归断言，不得留给 L3 手工或脚本复查代劳。L3 的驱动脚本判定函数自身也要有单测——判定过严会产出假失败，假失败比漏验更坏。触发口径：交付含渲染层可见变更才跑，纯文档 / 纯后台 / 纯数据 patch 不跑；**同一被测 commit 的 CDP 场最多 1 场、每版最多 2 场，第 3 场须先报公司负责人**；**实测 fail 后的复验场计入同一版场次、只验失败项，不得重跑已 pass 的腿**；场次已用满仍要复验时须负责人当场批一次，不批则本版不发；computer 场只在 diff 触及原生面板 / 系统通道时开。一场 = 2–3 条验收项、30 分钟墙钟硬上限、每完成一条腿立刻追加 digest 阶段行（静默 >20 分钟即故障），到点写现状 + 止损行收场，未验项随下一版或里程碑补，禁止用新场顶替旧场结论。

## 三、对外承诺与公开闭环（跨产品硬约束）

- **「已修复」的判据是公开收口（工程红线）**：代码合并并发布只是第一步，还必须 ①在公开工单回帖写明版本与验证证据并 close，②回到原始反馈处（帖子/评论区）回帖。三件缺一，对外一律算「未修复」，不许在内部标成已闭环。
- **对外承诺必须绑定一条 `schedule_enabled=1` 的定时任务**：写了「每 15 分钟巡检」「每日收集反馈」这类自动化承诺，就必须同时打开对应的钟并与承诺文案同批改；钟是关的，就不许这么写。承诺与配置不一致，是比功能缺失更难挽回的对外失真。
- **钟开着不等于在跑**：对外标「Active / 运行中」时，除 `scheduleEnabled=1` 外还须有该任务最近一次 run 的 `digest.md` 落盘。Host 把 run 记成 failed / `digestPath=null` 而磁盘 digest 存在，属 Host 记账假阴性：先报 runtime-feedback 修记账，不得据此关钟，也不得对外写「运行失败」。既无成功 run 也无 digest，才写「已配置、当前故障」或「筹备中」，不得标 Active。巡检任务连续失败要当作对外承诺的缺陷去修。
- **Release 正文必须来自仓内发布说明**：发布流程要把 `docs/release-notes/<version>.md` 写成 Release body（可在末尾附自动生成的 Full Changelog 行），不得只留 `--generate-notes` 的一行 changelog 链接——用户点开 Release 页看不到本版修了什么，等于没有发布说明。上线前核对 body 与仓内 notes 同口径（含「仍未闭环 / 未验证 / 待验」这类状态句）。但仓内 md 必须先合入、再写公开正文，避免两边打架。
- **大件产物上传必须分片/可续传，验收只看公开 URL**：单请求 PUT 在代理链路超过百兆量级会断链；上传脚本的单测通过不算完成，唯一验收是从公开 URL 下载后 sha256 与本地构建一致。
- **对外下载页必须指向最新正式 Release**：官网/下载页落后于实际发布，等于让所有新用户第一次摸到旧版；已知问题条目随版本更新，修复后改为已修复，不得中途消失。
- **开源仓库对外文档默认英文**：`README.md` 用英文（GitHub 仓库简介与 Topics 同步英文），中文另存 `README.zh-CN.md` 并在两版顶部互链；新增条目两版同批更新。已公开的历史 Release notes 不重写，语言口径从下一版起算。
- **榜单/平替页引用的数字必须可回溯**：对外榜单、平替页与宣传物料里的文件数、字节数、耗时、版本号只能引用产品仓已归档的实测证据，并标注冷跑/热跑口径；无证据的营销数字一律不许写，口径变化时先改产品仓证据再改物料。
- **远端发布走 Host 发布通道，不许把 push 转手给人跑命令**：给 origin 推 tag / ref 一律在产品的 ops 发布任务里用 `munk_task_publish`（tag + refs）执行，人类只在权限卡片上 `approve` 一次；不得以「Host 没有接口」为由让人类手敲 `git push`（交付 merge 只推分支，发布通道覆盖 tag）。被拒（如 `task_publish_remote_tag_conflict`）立即上报并停手，绝不强推、删远端 ref 或改指既有 tag。

## 四、全公司自治与协同准则

- **高频小步迭代**：每个产品的单期 `goal.md` 聚焦可独立验证的核心用户价值闭环；结案前必须经过真实运行态的体验走查与构建产物核验。
- **跨产品经验沉淀**：各产品在研发与巡检中验证有效的通用工程红线与避坑定论，只有具备跨产品普适价值（适用于 2 个及以上产品）时才上收写入本宪章；单一产品的特定业务逻辑留在产品自身目录。

## 五、研发 / 验证 / 发版三流解耦

研发节奏与发版节奏必须解耦：攒够一批再发，不按单个改动发版本。

- **运行时事实（Host）**：Host 用 **git worktree** 为每个 workitem 开独立工作树（`<repo>/.git/worktrees/<workItemId>`），合并走独立 `_merge` 工作树并可自动解**文本**冲突。因此并行写项之间不会互相踩树。合并后 workitem 即结束，产品侧没有「合并后再跑一次门」的环节：合并结果的整体门属 Host 层，产品只负责在自己工作树里跑全量 `code_gates`、把被测 commit 写进交付说明。
- **研发流**：完成定义 = 合入 main + 全量 `code_gates` + 相关专项门绿，**不等发版**。每产品同时最多 **3 个写项**并行 + **1–2 个只读项**（诊断 / 取证 / 只读验证）；再往上对单机是负收益。多步或大范围需求用 WorkSet 由 Planner 拆解规划。五条硬约束：① **计时类采样独占机器**（L2、公开包冷热跑、内存 / 多会话曲线），期间不叠编译、不叠其它 QA；② **单点文件只由版本收敛 / 发布收尾项独占**（`package.json#version`、`CHANGELOG`、README 版本表、`release.yml` 的 dispatch 默认 tag、当前版 release notes、发布证据文件），并行写项不得碰——文本冲突解得了，两个版本号各自"都对"解不了；③ **诊断项不得与它要诊断的修复项并行**（诊断测的是旧状态，修复一进另一条线结论即失真）；④ **发布通道每产品同时只允许一个 Release 在收口**；⑤ **交付前在自身工作树跑全量 gate**——产品交付即合并结束，不要求合并后重跑；worktree 绿即产品侧门结论，合并结果的整体验证归 Host。
- ops task（QA / 巡检 / 发版）与写项并行，但同样受 ① ④ 约束。
- **并行写项可以改同一文件**：delivery 合并阶段会自动解文本冲突，因此两条写项触及同一文件**不是禁忌**，不要为「避让」把写项串行化或回滚已发放的写项。真正的红线仍是上一条 ② 的**语义单点文件**：`package.json#version`、`CHANGELOG`、README 版本表、`release.yml` 的 dispatch 默认 tag、当前版 release notes、发布证据文件——这类文件被两条线各改出一个「自己都对」的版本时，文本冲突解得开、语义解不了，只能由版本收敛 / 发布收尾项独占。
- **main 工作区必须保持干净，脏改动不靠丢弃解决**：所有写动作都在 workitem 的 worktree 里发生；上面 ② 的语义单点文件不得在任何 session 的 main 工作区里直接手改，它们的修改只能由版本收敛 / 发布收尾项在自己 worktree 里做、过门、经 delivery 合并进 main。一旦出现脏工作区：① **禁止把内容原样丢弃**——`git checkout --` / `git restore` 掉带证据的改动等于无收益返工；② 正确路径是**先**把这份 diff 的逐字内容 / 证据搬进一个收口 workitem，**再**把 main 恢复 HEAD 让脏树归零（这一步是移位不是丢弃，且必须做，否则脏树会挡 delivery 合并）；③ 例外是纯文档一次性更正、且该文件无在飞项触碰：可授权一次 commit（只提交既有 diff、不改内容、不改版本 / tag / 通道），拿 sha 记账并当天收口，不许过夜。
- **任务不能提交代码**：ops task 对 codebase 是只读的，且 `bash git commit*` 被工具链 deny——给任务下「在 main 工作区提交」的指令必然跑到测试全绿后卡在 commit 再 abort。任何要落进代码仓的提交只能走 workitem（intake 拿正文 → 分支 commit → delivery 合并回 main）；任务/巡检只做只读核验与对外写操作。
- **次序约束必须卡在发放之前**：`pause-issuing` 只拦后续发放——Planner 提案一经确认，首个写项已经发放，事后再 pause 只挡得住第 2、3 项。凡要求「先提交 / 先收敛单点文件、再开写项」的次序，pause 必须在提案确认前落下。已发放的写项照常开工时不要回滚，只需核对破序是否让两条线同时改到语义单点文件，并把事实如实写进 digest 与交接，不得粉饰成「按序执行」。
- **发布流**：有当日迭代则次日 **07:00** 批次窗口发布，**没有需求就不发版**。07:00 只做到「构建 + 预检 + 公开件就绪」，推 tag 仍走发布通道并停在那张权限卡上等人点一次 `approve`，不把 `git push` 转手给人手敲。急修允许插队即时发，**仅限四类**：崩溃、数据损坏或丢失、公开版主链路不可用、安全；其余缺陷与新功能进次日窗口，同一天多个修复合并为一次发布。同一时间只允许一个正式 Release 在收口，口径为「tag → L1 结论 ≤1 小时」，不是整个长验收周期。
- **发版窗口必须回执**：07:00 批次窗口跑完，**成功与失败都必须唤醒产品负责人**——成功是里程碑事件（紧接着要跑 L1、按 L1 结论对外宣称、更新 README 与发布证据），失败要修；只有「无当日迭代，本窗口不发版」可以安静收工。定时跑没有 `notifyOwner` 参数，实现方式是在 digest 设 `needsOwner: true`，并用首行固定标记区分「发布成功 · 待 L1 / 对外收口」与「发布失败 · <失败项>」，不要让负责人把成功当故障分诊。L1 未过前不得对外写「已发布 / 已修复」。
- **长跑任务必须边跑边留痕**：QA / 巡检 / 发版这类要跑十几分钟以上的任务，开工即落 digest 骨架，并**每完成一条腿或一个阶段就追加一行**（阶段名、实测数字、当前判定），不得只在收工一次性回填。界面上的 digest 是人与负责人判断「在跑还是在死」的唯一信号，骨架长时间不动等于对外报故障。长跑任务的 digest 不是最终报告，是心跳。
- **发布点**：tag 打在**已过门的 commit** 上，可以指向 main 的历史提交。长验未完成的项不阻塞已验改动发布——发布点回退到该未验 commit 的父提交，本窗口只发它之前的。**禁止 cherry-pick 选择性拼版**。main 上存在未发布 commit 时，产品 `handoff.md` / `now.md` 必须显式记「未发布：`<sha>` `<标题>` `<原因>`」，下一窗口默认带上。只有单项验证预计跨多个窗口时，才给该工作项开临时分支，分支不参与发布，验完再合 main。
- **验证流**：L1 每版必验、L2 按 §二.4 条件触发；全量深验（多轮内存 / 多会话 / 并发）只给里程碑版（`x.y.0` 或每 4 周）。**发布后 L1 通过才可对外写「已发布 / 已修复」**；L1 不通过当天补发 patch，不撤已公开资产。
- **版本与文档**：批次发布按 patch 递增；`README` 与 Release notes 跟随批次统一改一次，不随单项改动各发一版。版本号收敛本身仍是一个研发项（要过门），不做进发布 task 里。
- **短验证不默认推到凌晨**：凡需人授权或人配合的实测（computer 场、真机、原生面板、发布前一次性验收），提请时必须同时给三档并写明**预计耗时与机器占用**：「现在跑」（预计 ≤30 分钟、不叠计时采样、人在场时默认推荐）、「夜间窗口跑」、「挂账并对外如实写未闭环」。禁止把半小时能收工的验证一律推到 03:00–06:00，也禁止在没有耗时估计的情况下把夜间窗口占成常态。选任何一档，失败都要当场落原因，不许连续静默失败。
- **运营任务只建常驻槽位，变更参数走 run brief**：每个产品 ops 项目按「验收 / 发版 / 对外收口 / 巡检」四类各留常驻 task，`instructions` 只写不变量（口径、判定线、完成定义、禁止项、证据落点）；版本号、dmg URL、sha256、被判目录、Issue 号这类每次都变的输入一律从 `POST /tasks/<id>/runs` 的 `brief` 传入，禁止写进 `instructions`。**定时跑（`scheduleCron`）没有 brief 通道**，所以定时 task 必须自足，要带参数的只能是手动触发的常驻 task。同一件事只允许一条 task，重复的合并或删掉。
- **一事一 task 是反模式**：一次性动作（改 Release body、补一条发布说明、仓内文档提交收口、清理本机副本）优先由发起它的 session 本场直接做完；确实要长跑、独占机器或 computer 场才开 task，且复用既有常驻 task 的 brief，不新建。用完的一次性 task 由产品负责人**归档**，不走 `DELETE`。**定时任务本身不是一次性 task**，不适用「用完归档」：它按 `scheduleCron` 长期复用，`instructions` 自足即可。
- **brief 必须回抄进 digest 首段**：Host 不回存 brief，digest 首段的 brief 全文是该场口径唯一可回查锚；删 task 前先确认结论已落 digest / case / qa-checklist，不依赖 task 记录留存。
